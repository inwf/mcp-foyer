# 性能与 MCP 兼容性验证

本轮针对个人本机、几十到上百个上游的工具发现路径。先区分三种成本：
mcp-foyer 查目录和序列化的成本、上游进程与网络的成本、模型选择和调用工具的成本。
下面的基准覆盖第一种；不要据此推断真实上游的内存占用或模型任务成功率。

## 可重复的目录基准

在仓库根目录进入后端后运行：

```sh
cd backend
go test -buildvcs=false ./internal/gateway -run '^$' \
  -bench 'Benchmark(SearchDirectory|SystemToolList)' -benchmem -benchtime=500ms -count=3
```

固定数据规模为 20×50、100×50、100×100（服务器数×每台工具数）。工具默认不暴露，
名称按编号排列，每个 schema 约 1.5 KiB。`documents` 查询匹配全部工具，考察
宽查询的扫描与排序成本。还测单服务器浏览、固定返回 5 个摘要、返回 2 个完整 schema。

使用注入的缓存目录和 Go SDK 内存传输，测量包括系统工具的协议往返及结果编码。
配置读取使用真实配置管理器。没有拉起成百个上游进程，也不包括 HTTP 网络往返。
实际连接管理器复制缓存切片的成本、启动和重连成本不在这组基准中。

- `ns/op`：一次操作的平均耗时。
- `B/op`、`allocs/op`：每次操作的临时分配，**不是常驻内存 RSS**。
- `response-B`：完整 MCP 结果对象的 JSON 字节数，不含 JSON-RPC 和 HTTP 外壳。
  对工具调用包含 `content` 和 `structuredContent` 两部分，不等同于模型输入 token。

## 本次测量

2026-09-11，macOS / Apple M5 / arm64，Go 1.26.5，Go MCP SDK v1.7.0。
每项运行三次，表中耗时取三次平均值的中位数；这不是单次请求分布的 p50 或 p95。
改造前使用开始实施时的源码备份，两侧使用相同数据和基准代码。

| 场景 | 改造前 | 改造后 | 备注 |
| --- | ---: | ---: | --- |
| 系统 `tools/list` | 0.438 ms / 6,945 B | 0.340 ms / 5,285 B | 7 个系统工具变为 4 个 |
| 1,000 工具，默认搜索 | 0.365 ms / 5,435 B | 0.300 ms / 1,873 B | 默认数量从 20 变为 5，增加游标 |
| 5,000 工具，默认搜索 | 0.759 ms / 5,435 B | 0.877 ms / 1,873 B | 相同宽查询 |
| 10,000 工具，默认搜索 | 1.096 ms / 5,435 B | 1.481 ms / 1,873 B | 增加服务器元数据匹配及分页校验 |
| 10,000 工具，带 2 个 schema | — | 1.585 ms / 7,485 B | 新增能力 |
| 100 台、每台 100 工具，浏览一台 | — | 0.165 ms / 1,867 B | 默认 5 个摘要 |

系统工具清单缩小约 **24%**，默认搜索响应缩小约 **66%**。默认搜索的响应对比
包含了返回数量变化，不能当作相同结果数下的压缩率。两侧都显式请求 5 条时，
响应由 1,535 B 增至 1,873 B，主要增加分页游标。

全目录搜索在最大规模下仍比旧版多约 0.39 ms；分页与更完整的匹配范围不是零成本。
该规模的默认搜索临时分配约由 4.41 MB/op 降到 3.47 MB/op。这里的收益主要是
更小的初始清单、可控制的发现响应，以及可在一次搜索中拿到 schema，不能宣称
所有路径都更快或模型一定少用多少 token。

## 分字段 BM25（2026-09-13）

搜索由子串匹配换成分词加分字段 BM25（`REFACTOR_PLAN.md` P12），每次搜索对
当前候选建一次倒排索引。同一台机器、同一组基准，与上一节「改造后」对比：

| 场景 | 子串匹配 | BM25 | 备注 |
| --- | ---: | ---: | --- |
| 1,000 工具，默认搜索 | 0.300 ms | 0.95 ms | 响应字节不变 |
| 5,000 工具，默认搜索 | 0.877 ms | 5.36 ms | |
| 10,000 工具，默认搜索 | 1.481 ms | 8.06 ms | 临时分配 3.47 → 8.94 MB/op |
| 10,000 工具，带 2 个 schema | 1.585 ms | 7.84 ms | |
| 100 台、每台 100 工具，浏览一台 | 0.165 ms | 0.25 ms | 只索引那一台 |

第一版按文档建 map，10,000 工具时 37 ms；改为倒排索引、分词结果尽量取原串
的子串、同一服务器的三个字段只分词一次之后降到 8 ms。剩下的成本主要是每个
词出现一次就查一次 map。它在计划设定的「劣化一个量级」阈值之内，且一次搜索
远小于一次模型往返，所以没有再做上游刷新时预分词的缓存；如果目录规模超过
这组基准，那是下一步。

排序质量不在这组基准里。它由 `internal/gateway/testdata/search_corpus.json`
和 `search_ranking_test.go` 的查询表衡量：换算法前那张表有 8 行失败（改拼法的
名字、中文非连续片段、长描述靠碰运气命中更多词），换算法后全部通过，原先通过
的 18 行也没有变化。

### 参数名进入索引（2026-09-19）

搜索范围加上每个工具输入 schema 里的参数名与参数描述（`ArgumentText` 展平，
权重 0.5，最低）。这是 Anthropic 工具搜索的做法，让只知道要传什么参数的调用方
也能找到工具。10,000 工具的默认搜索由 8.06 ms 变为 10.8 ms，临时分配 8.94 MB
变为 12.2 MB；响应字节不变。第一版每次搜索把每个 schema 经 JSON 往返一次，
80 ms，给已解码的 map 加直接路径后回到这个数字。查询表新增 7 行按参数查找的
案例，全部通过。

## 功能及跨语言兼容性

```sh
make check
make build
```

`make check` 包含 Go 格式、vet、race 测试和前端 typecheck、oxlint、Vitest。
回归覆盖分页边界、游标失效范围、完整大 schema、隐藏工具、同名工具路由、通用配置
校验，以及 stdio 和 HTTP 上游的业务 `tags` 透传。

实际 TypeScript MCP SDK 检查是可选项，避免把 SDK 加入前端运行依赖。
用 pnpm 装在独立目录，然后运行这一个 Go 集成测试：

```sh
MCP_FOYER_INTEROP_DIR="$(mktemp -d)"
pnpm --dir "$MCP_FOYER_INTEROP_DIR" add --ignore-scripts @modelcontextprotocol/sdk@1.30.0
cd backend
go test -buildvcs=false ./internal/integration -run '^TestTypeScriptSDK' -count=1 -v \
  -args -mcp-ts-sdk-dir="$MCP_FOYER_INTEROP_DIR"
```

这段命令从仓库根目录执行。测试自动启动临时本机端口和测试上游，不用实际配置。
SDK 会解析 `tools/list`，再检查系统工具自查、带 schema 的分页结果、详情、调用和
业务 `tags`。不指定安装目录时，该项测试跳过；常规 Go schema 保护测试始终运行。
本轮已使用 pnpm 安装的 SDK 1.30.0 实测通过。

文档清单和 schema 的防漂移检查也做了反向验证：临时把文档表里的新名字改回旧名字，
以及把搜索结果的 schema 字段改成会生成布尔属性 schema 的类型，均确认对应测试失败，
再恢复正确代码。

## 测自己的真实使用场景

用单独的数据目录和配置，保留日常实例。先选 10 台、30 台、100 台测试上游，
记录 stdio / HTTP 比例；每组固定工具数和 schema 大小，再逐步增加规模。

| 路径 | 建议记录 |
| --- | --- |
| 启动与重连 | API 就绪时间、首台和全部上游就绪时间、失败与重试数量 |
| 空闲及持续运行 | mcp-foyer 进程 RSS、全部子进程 RSS、CPU、文件描述符和连接数 |
| 工具发现 | 首次/后续搜索、空结果、多词搜索、分页、schema 模式的 p50/p95 和响应字节数 |
| 工具调用 | 单个调用和少量并发调用的延迟、超时、取消、错误率 |
| 故障恢复 | 慢上游、断线、进程退出、工具列表变化时，其他上游是否仍能正常用 |

个人使用先测试并发 1、2、5；负载用测试 MCP 服务器或无副作用的工具，避免业务操作
污染数据。把 mcp-foyer 与上游指标分开记录：100 个 Node/Python 进程的占用通常不能靠
调整搜索接口解决。需要查 mcp-foyer 的热点时，可给基准加 `-cpuprofile` / `-memprofile`，
再用 `go tool pprof` 分析。

如果要评价模型效率，固定模型、提示词、工具目录和一组真实任务，重复比较工具发现
轮次、工具选择正确率、参数正确率、成功率、端到端耗时及模型实际使用的 token。
字节数变化只说明协议负载变化，不能代替这组任务评测。本轮没有进行模型 A/B 实验。
