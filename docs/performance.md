# 性能与 MCP 兼容性验证

本轮针对个人本机、几十到上百个上游的工具发现路径。先区分三种成本：
mcp-foyer 查目录和序列化的成本、上游进程与网络的成本、模型选择和调用工具的成本。
下面的基准覆盖第一种；不要据此推断真实上游的内存占用或模型任务成功率。

## 可重复的目录基准

在仓库根目录进入后端后运行：

```sh
cd backend
go test -buildvcs=false ./internal/gateway -run '^$' \
  -bench 'Benchmark(SearchDirectory|SystemToolList)' -benchmem -benchtime=500ms -count=3
```

固定数据规模为 20×50、100×50、100×100（服务器数×每台工具数）。工具默认不暴露，
名称按编号排列，每个 schema 约 1.5 KiB。`documents` 查询匹配全部工具，考察
宽查询的扫描与排序成本。还测单服务器浏览、固定返回 5 个摘要、返回 2 个完整 schema。

使用注入的缓存目录和 Go SDK 内存传输，测量包括系统工具的协议往返及结果编码。
配置读取使用真实配置管理器。没有拉起成百个上游进程，也不包括 HTTP 网络往返。
实际连接管理器复制缓存切片的成本、启动和重连成本不在这组基准中。

- `ns/op`：一次操作的平均耗时。
- `B/op`、`allocs/op`：每次操作的临时分配，**不是常驻内存 RSS**。
- `response-B`：完整 MCP 结果对象的 JSON 字节数，不含 JSON-RPC 和 HTTP 外壳。
  对工具调用包含 `content` 和 `structuredContent` 两部分，不等同于模型输入 token。

## 本次测量

2026-09-11，macOS / Apple M5 / arm64，Go 1.26.5，Go MCP SDK v1.7.0。
每项运行三次，表中耗时取三次平均值的中位数；这不是单次请求分布的 p50 或 p95。
改造前使用开始实施时的源码备份，两侧使用相同数据和基准代码。

| 场景 | 改造前 | 改造后 | 备注 |
| --- | ---: | ---: | --- |
| 系统 `tools/list` | 0.438 ms / 6,945 B | 0.340 ms / 5,285 B | 7 个系统工具变为 4 个 |
| 1,000 工具，默认搜索 | 0.365 ms / 5,435 B | 0.300 ms / 1,873 B | 默认数量从 20 变为 5，增加游标 |
| 5,000 工具，默认搜索 | 0.759 ms / 5,435 B | 0.877 ms / 1,873 B | 相同宽查询 |
| 10,000 工具，默认搜索 | 1.096 ms / 5,435 B | 1.481 ms / 1,873 B | 增加服务器元数据匹配及分页校验 |
| 10,000 工具，带 2 个 schema | — | 1.585 ms / 7,485 B | 新增能力 |
| 100 台、每台 100 工具，浏览一台 | — | 0.165 ms / 1,867 B | 默认 5 个摘要 |

系统工具清单缩小约 **24%**，默认搜索响应缩小约 **66%**。默认搜索的响应对比
包含了返回数量变化，不能当作相同结果数下的压缩率。两侧都显式请求 5 条时，
响应由 1,535 B 增至 1,873 B，主要增加分页游标。

全目录搜索在最大规模下仍比旧版多约 0.39 ms；分页与更完整的匹配范围不是零成本。
该规模的默认搜索临时分配约由 4.41 MB/op 降到 3.47 MB/op。这里的收益主要是
更小的初始清单、可控制的发现响应，以及可在一次搜索中拿到 schema，不能宣称
所有路径都更快或模型一定少用多少 token。

## 分字段 BM25（2026-09-13）

搜索由子串匹配换成分词加分字段 BM25（`REFACTOR_PLAN.md` P12），每次搜索对
当前候选建一次倒排索引。同一台机器、同一组基准，与上一节「改造后」对比：

| 场景 | 子串匹配 | BM25 | 备注 |
| --- | ---: | ---: | --- |
| 1,000 工具，默认搜索 | 0.300 ms | 0.95 ms | 响应字节不变 |
| 5,000 工具，默认搜索 | 0.877 ms | 5.36 ms | |
| 10,000 工具，默认搜索 | 1.481 ms | 8.06 ms | 临时分配 3.47 → 8.94 MB/op |
| 10,000 工具，带 2 个 schema | 1.585 ms | 7.84 ms | |
| 100 台、每台 100 工具，浏览一台 | 0.165 ms | 0.25 ms | 只索引那一台 |

第一版按文档建 map，10,000 工具时 37 ms；改为倒排索引、分词结果尽量取原串
的子串、同一服务器的三个字段只分词一次之后降到 8 ms。剩下的成本主要是每个
词出现一次就查一次 map。它在计划设定的「劣化一个量级」阈值之内，且一次搜索
远小于一次模型往返，所以没有再做上游刷新时预分词的缓存；如果目录规模超过
这组基准，那是下一步。

排序质量不在这组基准里。它由 `internal/gateway/testdata/search_corpus.json`
和 `search_ranking_test.go` 的查询表衡量：换算法前那张表有 8 行失败（改拼法的
名字、中文非连续片段、长描述靠碰运气命中更多词），换算法后全部通过，原先通过
的 18 行也没有变化。

### 参数名进入索引（2026-09-19）

搜索范围加上每个工具输入 schema 里的参数名与参数描述（`ArgumentText` 展平，
权重 0.5，最低）。这是 Anthropic 工具搜索的做法，让只知道要传什么参数的调用方
也能找到工具。10,000 工具的默认搜索由 8.06 ms 变为 10.8 ms，临时分配 8.94 MB
变为 12.2 MB；响应字节不变。第一版每次搜索把每个 schema 经 JSON 往返一次，
80 ms，给已解码的 map 加直接路径后回到这个数字。查询表新增 7 行按参数查找的
案例，全部通过。

### 整体拼写与长度折减（2026-10-07）

名字与参数名的整体形式改为按写出的拼写归档，查询一侧同时带折叠复数的拼写（P20）。
`readfile` 只命中 `read_file`，不再落到孪生的 `read_files` 上；`listissues` 这类
连写复数查询仍然有效。同一组基准，10,000 工具：

| 场景 | 之前 | 之后 | 备注 |
| --- | ---: | ---: | --- |
| 默认搜索 | 10.8 ms / 12.2 MB | 11.5 ms / 12.2 MB | 响应字节 1,873 → 1,863，分数位数变化 |
| 带 2 个 schema | — | 11.5 ms / 12.3 MB | 响应 7,481 B |

第一版把同一段文本拆了两次词，默认搜索升到约 14 ms、临时分配 13.7 MB；改成拆
一次、折叠作为第二遍之后回到上表。BM25 的长度折减参数 b 由 0.75 降到 0.6：真实
工具描述从一行到数段不等，在目录规模下，标准折减让字段最短的相似邻居排到调用
方要的工具前面。排序质量由新增的规模用例衡量（`search_scale_test.go`，20×50、
100×50、100×100 三个档位）：目标工具进入 top-3 的比例由 79.4%、82.4%、76.5%
升到 91.2%、91.2%、88.2%，原语料的 34 行 top-1 断言全部保持。

### 常见词、摊平与封顶（2026-10-07）

`the`、`what`、`my` 这类虚词不再参与匹配与计分，除非它们出现在工具名或服务器名里
（`commonwords.go`）。此前一句话形状的查询会把噪声当成答案：
`what does the acme toolkit do` 返回 17 条命中，全部由 what、the、do 撑起，
acme 与 toolkit 一个都没命中；现在返回 0 条，并把没命中的词列进 `unmatched`。
词表只收函数词，不用词频阈值：阈值在十台工具的目录和一万台的目录上会给出不同
答案，还会在文件类目录里砍掉调用方真正要的 `file`。第一版把参数文本也算作
「名字」，而参数描述是散文（「the maximum number of results」），`the` 因此对
整张表豁免、规则形同虚设；线上复测当天改为只看工具名与服务器名。

同批三件小的：跨服务器搜索把命中摊开，每台最多两条（命中只来自一台时不受限）；
`unavailable` 最多列五条，其余由 `unavailableMore` 计数；规模套件的服务器名从
第 101 台起带轮次后缀，与真实安装一样唯一，不再出现十个 `docs-mcp` 撞在一起。

规模基准新增 1000×30 档（30,093 个候选）：

| 目录 | 默认搜索 | 响应 |
| --- | ---: | ---: |
| 100×100（10,093 个候选） | 13.7 ms / 11.9 MB | 1,863 B |
| 1000×30（30,093 个候选） | 34.8 ms / 37.2 MB | 1,863 B |

开销随目录线性（工具数 ×3，时间与临时分配约 ×2.5），响应字节不变。同一档位上一轮
记录为 11.5 ms / 12.2 MB；差值可能来自测量波动，也可能来自摊平按分数顺序走的那一遍
命中，没有分离。索引仍按每次搜索重建，目录再上一个数量级之前要先做常驻索引与
增量更新。规模套件的 top-3 命中率在新档位为 94.1%（32/34），两条记录在案的落空：
`listChannels`、`knowledge graph search`。四个档位共撤销一条记录：
`how do I read a file` 由落空转为命中——虚词不再参与计分后，read 与 file 不再被
do、a 这类词稀释；100×50 档的命中率随之由 91.2% 升到 94.1%。

### 语义排序与嵌入索引（2026-10-07）

搜索路径多了一条可选分支：开启嵌入模型后，`search_tools` 照旧按字面排序，再把两
边的名次融合（RRF，k=60），字面零命中而相似度达标的工具因此也能出现。融合只在
模型面（`search_tools`）生效；管理 API 与 CLI 的搜索保持字面排序，那是人在搜索框
里打字，要的是即时过滤。关闭时（默认）代码走原路：语料、规模与基准全部不动。

每次搜索的额外成本是**一次查询嵌入调用**（同一查询在 64 条缓存内只调一次，翻页
不重复付费）加上融合本身。融合的处理器开销由同一组 30,000 个候选 A/B 量出（下
面的命令，`-count=3` 取中位；此处的生成目录是 3,750 台×8 个工具，与上文表格的
1,000×30 不同，所以只有两个数之差是可比的）：

```sh
cd backend
go test -buildvcs=false ./internal/gateway -run '^$' \
  -bench 'BenchmarkSearch(Lexical|Fused)OverThirtyThousand' -benchmem -benchtime=500ms -count=3
```

| 路径 | 耗时 | 临时分配 |
| --- | ---: | ---: |
| 纯字面 | 53.6 ms | 51.0 MB |
| 字面 + 语义融合 | 59.2 ms | 51.8 MB |

索引与网络那一半不在这组基准里：建索引每 32 个工具发一次请求；索引文件按
4 字节×维度×工具数 增长（1,024 维、30,000 个工具约 123 MB，384 维约 46 MB）。
查询嵌入的延迟取决于所连的服务，这里不猜。

质量那一半没有在这份文档里量：相似度与门槛的取值取决于模型，只有在真实目录上
才说得清。设置页的效果预览（同一条查询看两边排序）与规模套件是工具；用真实模型
量出的数字应当补进这一节。

### 查询点名服务器与命中必填参数（2026-10-10）

`search_tools` 的两处变化（P25）：查询里有一个词等于某台已连接服务器的名字时，这次
搜索按那台收窄，输出里的 `server` 回显收窄后的名字；每条命中带 `requiredArgs`，
列出该工具输入 schema 顶层的必填参数名。同一组基准，响应字节：

| 场景 | 之前 | 之后 | 备注 |
| --- | ---: | ---: | --- |
| 1,000 工具，默认搜索 | 1,863 B | 1,863 B | 基准夹具的工具没有必填参数，`requiredArgs` 不出现 |
| 10,000 工具，带 2 个 schema | 7,481 B | 7,481 B | 同上 |
| 系统 `tools/list` | 5,285 B（2026-09-11） | 6,978 B | 中间几轮搜索改动的累计，本轮加入 `requiredArgs` 属性与 `search_tools` 的两处说明文字 |

有必填参数时，每条命中增加一个字符串数组，长度由该工具自己的必填参数个数决定。
收窄在排序之前完成：对查询词与服务器名做拆词比较，成本按词数与服务器数相乘；
基准夹具里没有名字能对上查询词的服务器，这组耗时不含这条路径。1000×30 档默认
搜索本轮为 41.4 ms / 44.1 MB，上一轮记录 34.8 ms / 37.2 MB；同一档位在相邻两轮
记录中差过 19%（11.5 与 13.7 ms），这次按同一量级的测量漂移看待，不与改动挂钩。
本轮每次搜索新增的处理器成本在微秒级：按词比较一遍服务器名，每条命中读一次缓存
schema 的必填列表。

### 词干、中文单字与浮点排序（2026-10-30）

英文词改为还原成 Snowball 词干（原先只折叠复数），描述里的中文另外按单字索引，
工具名以服务器名开头时多索引一个去掉前缀的整体拼写，排序改用未取整的分数。
同一组基准：

| 场景 | 之前 | 之后 |
| --- | ---: | ---: |
| 20×50，默认搜索 | — | 1.8 ms / 1.9 MB |
| 100×50，默认搜索 | — | 8.6 ms / 7.1 MB |
| 100×100，默认搜索 | 13.7 ms / 11.9 MB | 16.1 ms / 14.1 MB |
| 1000×30，默认搜索 | 41.4 ms / 44.1 MB | 49.0 ms / 45.6 MB |
| 30,000 候选，纯字面 | 53.6 ms / 51.0 MB | 74.2 ms / 49.7 MB |
| 30,000 候选，融合 | 59.2 ms / 51.8 MB | 75.6 ms / 50.0 MB |

响应字节不变（默认 1,863 B，带 2 个 schema 7,481 B）。词干算法本身很慢：不缓存时
100×100 档是 47 ms，其中词干占 37% 的处理器时间。现在每个词的词干只算一次，存进
进程内的表，表的大小等于目录的词汇量，搜索过一次之后就不再增长。剩余的开销来自
中文单字多出的词项和去前缀的整体拼写。

## 功能及跨语言兼容性

```sh
make check
make build
```

`make check` 包含 Go 格式、vet、race 测试和前端 typecheck、oxlint、Vitest。
回归覆盖分页边界、游标失效范围、完整大 schema、隐藏工具、同名工具路由、通用配置
校验，以及 stdio 和 HTTP 上游的业务 `tags` 透传。

实际 TypeScript MCP SDK 检查是可选项，避免把 SDK 加入前端运行依赖。
用 pnpm 装在独立目录，然后运行这一个 Go 集成测试：

```sh
MCP_FOYER_INTEROP_DIR="$(mktemp -d)"
pnpm --dir "$MCP_FOYER_INTEROP_DIR" add --ignore-scripts @modelcontextprotocol/sdk@1.30.0
cd backend
go test -buildvcs=false ./internal/integration -run '^TestTypeScriptSDK' -count=1 -v \
  -args -mcp-ts-sdk-dir="$MCP_FOYER_INTEROP_DIR"
```

这段命令从仓库根目录执行。测试自动启动临时本机端口和测试上游，不用实际配置。
SDK 会解析 `tools/list`，再检查系统工具自查、带 schema 的分页结果、详情、调用和
业务 `tags`。不指定安装目录时，该项测试跳过；常规 Go schema 保护测试始终运行。
本轮已使用 pnpm 安装的 SDK 1.30.0 实测通过。

文档清单和 schema 的防漂移检查也做了反向验证：临时把文档表里的新名字改回旧名字，
以及把搜索结果的 schema 字段改成会生成布尔属性 schema 的类型，均确认对应测试失败，
再恢复正确代码。

## 测自己的真实使用场景

用单独的数据目录和配置，保留日常实例。先选 10 台、30 台、100 台测试上游，
记录 stdio / HTTP 比例；每组固定工具数和 schema 大小，再逐步增加规模。

| 路径 | 建议记录 |
| --- | --- |
| 启动与重连 | API 就绪时间、首台和全部上游就绪时间、失败与重试数量 |
| 空闲及持续运行 | mcp-foyer 进程 RSS、全部子进程 RSS、CPU、文件描述符和连接数 |
| 工具发现 | 首次/后续搜索、空结果、多词搜索、分页、schema 模式的 p50/p95 和响应字节数 |
| 工具调用 | 单个调用和少量并发调用的延迟、超时、取消、错误率 |
| 故障恢复 | 慢上游、断线、进程退出、工具列表变化时，其他上游是否仍能正常用 |

个人使用先测试并发 1、2、5；负载用测试 MCP 服务器或无副作用的工具，避免业务操作
污染数据。把 mcp-foyer 与上游指标分开记录：100 个 Node/Python 进程的占用通常不能靠
调整搜索接口解决。需要查 mcp-foyer 的热点时，可给基准加 `-cpuprofile` / `-memprofile`，
再用 `go tool pprof` 分析。

如果要评价模型效率，固定模型、提示词、工具目录和一组真实任务，重复比较工具发现
轮次、工具选择正确率、参数正确率、成功率、端到端耗时及模型实际使用的 token。
字节数变化只说明协议负载变化，不能代替这组任务评测。本轮没有进行模型 A/B 实验。
